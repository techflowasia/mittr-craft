## How Part A ran

- **Stub platform.** `scripts/mittr/stub-platform.mjs` (new, tracked, with an 8-test suite) listens on `127.0.0.1` only. For accounts SA and SB it answers:
  - `/auth/desktop/{start,exchange,refresh}` (PKCE checked);
  - `/desktop/{catalog,work}`;
  - `/api/integrations` and its two test routes, in the develop shape (with `workspaceSlugs`) or the main shape (without);
  - `/api/quota/me`;
  - `/v1/chat/completions`, a stub model that calls the `skill` tool or the connector through `execute` when asked, and otherwise answers.

  It counts requests per path and records what the model was offered, never a header or a token. Its replies carry extra fields (`id`, `webhookSecret`, `tokenPreview`, `ownerId`, `accountId`) so the whitelist checks can see them dropped. For the re-check, its Plane test reply also carries `workspaceId` and, per workspace, `id` and `projects`.
- **Catalog.**
  - SA: skill `card-analysis` and connector `stub-law`, a local stdio `scripts/mittr/stub-mcp-server.mjs` run by an absolute `node` path.
  - SB: skill `notes`, no connectors.
- **Work.**
  - SA: `MRKB-1` (Jira), `TF-7` (Plane `techflow`), `MIT-3` (Plane `mittr`).
  - SB: `OPS-2` (Plane `ops`).
  - Every URL is under `.invalid`.
- **Launches.** Five, each recorded with the holder of 57133 (free every time).
  - Desktop scenario A: fresh temp HOME, then one relaunch of the same HOME for the P3-09 start count.
  - Desktop scenario B: a second fresh temp HOME, with the stub in the main shape.
  - The packed `mittrcraft serve`: three starts (F7).

  Each desktop launch ran `env -i` with:
  - `HOME`, `TMPDIR` and every `XDG_*` inside a fresh `p3.XXXX` temp dir;
  - `OPENCHAMBER_DESKTOP_USER_DATA_DIR=<temp>/userData`;
  - `MITTRCRAFT_BROKER_URL=http://127.0.0.1:<stub>` and `MITTRCRAFT_SHIM_LOG=1`;
  - dummy `JIRA_TOKEN` and `PLANE_API_KEY` (random, held only in the launching shell);
  - Chromium's `--use-mock-keychain`, and a loopback DevTools port on the test PID.

  A seeded `desktopLocalPort` kept the app off 57133. It bound 57361 every time. Each app was quit with `kill -TERM <pid>` after checking the binary path, and every descendant was then confirmed gone.
- **Port guard (R46).** Every HTTP call to the app, the stub or the DevTools port first checked that the listener was the test PID or its descendant. 451 calls passed the guard and none was refused.
- **Sign-in.**
  - The controller called `POST /api/mittr/auth/start` and checked that `authorizeUrl` pointed at the stub.
  - It followed that URL with `curl`, not a browser, and read the `mittrcraft-dev://auth/callback?code=…` location.
  - It posted that location to `/api/mittr/auth/callback`.

  No browser was opened by the controller.
- **UI.** The test window was driven through its own DevTools port (loopback, test PID only):
  - DOM reads, clicks and typed text;
  - `Page.captureScreenshot`.

  Links were recorded instead of opened: for the length of one click, the page's runtime API took its "open external URL" branch into a recorder.
- **Watchers.**
  - Egress: `lsof` every 0.3 s over the app PID and all descendants, logging each new non-loopback peer.
  - Keychain prompts: `pgrep -x SecurityAgent` every 0.3 s.
  - The hosted server also ran with a Node `connect` guard that refuses and logs any non-loopback host. Its engine ran under `sandbox-exec` with outbound limited to loopback.

6. Platform, not shipped now: `8d1a35118` (dev reads a new connection up to 10 minutes later) and `3da0045f7` (prod keeps one Plane workspace).

From the ledger and this gate:

8. **R120/R128 — the listing hook for org connectors (+1, 34 → 35).** Org connectors are not listed in Settings → MCP (M4). A read-only, redacted listing needs one hook. Meanwhile the work-status panel already counts them (F14).
9. **I3 — hosted secrets, `/api/config` and the desktop tunnel.**
   - Choose between a proxy redaction hook for `mcp.servers.*.headers`, `environment` and `oauth.client_secret` (+1) and keeping connectors off hosted web (today's R132 default, M7).
   - The same `GET /api/config` read returns the rest of the managed file, including the shim's settings, to every hosted UI session (F15).
   - On hosted web, My work and Work tracking use the one shared Mittr account, so any directory user can read its work or replace its Jira/Plane token (preflight F35).
   - Agent file tools running as the same user can read the 0600 managed file and the catalog cache.
10. **I3, continued — the desktop tunnel.** A tunnel opened after start, without a UI password, lets connect-link clients reach the same `GET /api/config`. R132 decides "hosted" only at start.
11. **Settings search (+1).** Work tracking is not found by Settings search; adding it needs `search.ts`.
12. **R136.** On a single-workspace platform, Add shows while no workspace is saved and hides after (T5). Hiding it entirely would block Plane setup on prod.
13. **Org skills under a personal `OPENCODE_CONFIG_DIR`** (R126). When a person points the engine at their own config folder, org skills are written there too.
14. **Enablement is per machine**, as in 1.22. One account's disable applies to every account on the Mac (preflight F34).
15. **The upstream fetches in F3 and BX1** (findings 3 and 20), and the usage-reports switch: disable or gate them in the Mittr product.
16. **Model calls nobody asked for, on the Mittr quota:** the recap calls (F9) and the unattributed call (finding 24).
17. **`.mittr` notice items:** none came up in this gate.
18. **Org connectors are new egress (preflight F16).** In the product, every org connector connects at each engine location start, for every user: the handshake and tool list, and an `npx` install for a local one. 1.22 never did this. On an upgraded Mac it starts at the first 2.x start, from the cached 1.22 catalog, before any sync. Decision 5 covers only the gate run.
19. **A repository can take over an org connector's name for its project.** A project's own `opencode.json` (or `.opencode/opencode.json`) with an mcp entry of the same name replaces the org connector for that project (engine proof, "Project layer"). No secret moves: the org connector's headers did not reach the repository's server. But the person then talks to the repository's server under the org connector's name, and R130 cannot see project layers.
20. **For the record — R130's wording.** R130 says the engine deep-merges config layers. For MCP entries between the managed and the project layers, on engine 2.0.22, a same-name entry **replaces** the other whole; it does not deep-merge.
21. **Upstream's GitHub token use (BI7, finding 22). Decided: leave it as upstream**, recorded as known behaviour. Anyone signed in to `gh` has their token used, and `api.github.com` contacted, at every start.
22. **Upstream's third-party coding-CLI card (F-B5, finding 23).** Hide it or keep it. It names another AI vendor's product on a MittrCraft screen.
23. **Gate builds share their name and bundle id with the installed Dev 1.x (I7).** Some other automation on this machine pressed Sign in in a test window in phase 2, in Part A (F4) and again in the re-check (finding 30), and the callback went to the test app only because it was running. Suggested: build gate apps with their own name, bundle id and URL scheme, and check System Settings → Privacy → Accessibility for other controllers before a run.
24. **Go work's first turn (BX2, finding 21).** Accept that the agent fetches the card's URL on the person's machine with no prompt, or have Go work pass the card's details instead.
25. **Plane on dev. Decided: not run.** The owner has no Plane account (finding 27).
