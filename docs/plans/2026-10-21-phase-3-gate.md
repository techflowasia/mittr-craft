- **Stub platform.** `scripts/mittr/stub-platform.mjs` (new, tracked, with an 8-test suite) listens on `127.0.0.1` only. For accounts SA and SB it answers:

  - `/api/integrations` and its two test routes, in the develop shape (with `workspaceSlugs`) or the main shape (without);

  - `/v1/chat/completions`, a stub model that calls the `skill` tool or the connector through `execute` when asked, and otherwise answers.

  - SB: `OPS-2` (Plane `ops`).
  - Every URL is under `.invalid`.
- **Launches.** Five, each recorded with the holder of 57133 (free every time).
  - Desktop scenario A: fresh temp HOME, then one relaunch of the same HOME for the P3-09 start count.
  - Desktop scenario B: a second fresh temp HOME, with the stub in the main shape.
  - The packed `mittrcraft serve`: three starts (F7).

  Each desktop launch ran `env -i` with:
  - `HOME`, `TMPDIR` and every `XDG_*` inside a fresh `p3.XXXX` temp dir;
  - `OPENCHAMBER_DESKTOP_USER_DATA_DIR=<temp>/userData`;
  - `MITTRCRAFT_BROKER_URL=http://127.0.0.1:<stub>` and `MITTRCRAFT_SHIM_LOG=1`;
  - dummy `JIRA_TOKEN` and `PLANE_API_KEY` (random, held only in the launching shell);
  - Chromium's `--use-mock-keychain`, and a loopback DevTools port on the test PID.

  A seeded `desktopLocalPort` kept the app off 57133. It bound 57361 every time. Each app was quit with `kill -TERM <pid>` after checking the binary path, and every descendant was then confirmed gone.
- **Port guard (R46).** Every HTTP call to the app, the stub or the DevTools port first checked that the listener was the test PID or its descendant. 451 calls passed the guard and none was refused.
- **Sign-in.**
  - The controller called `POST /api/mittr/auth/start` and checked that `authorizeUrl` pointed at the stub.
  - It followed that URL with `curl`, not a browser, and read the `mittrcraft-dev://auth/callback?code=…` location.
  - It posted that location to `/api/mittr/auth/callback`.

  No browser was opened by the controller.
- **UI.** The test window was driven through its own DevTools port (loopback, test PID only):
  - DOM reads, clicks and typed text;
  - `Page.captureScreenshot`.

  Links were recorded instead of opened: for the length of one click, the page's runtime API took its "open external URL" branch into a recorder.
- **Watchers.**
  - Egress: `lsof` every 0.3 s over the app PID and all descendants, logging each new non-loopback peer.
  - Keychain prompts: `pgrep -x SecurityAgent` every 0.3 s.
  - The hosted server also ran with a Node `connect` guard that refuses and logs any non-loopback host. Its engine ran under `sandbox-exec` with outbound limited to loopback.

## Findings

1. **F1 — the leak scan fails on a log line (product defect).** R130's left-out message in `packages/mittr-server/src/mittr/mcp-fragment.js` reads "an MCP server named … is already in the person's own OpenCode config". It is packed into `app.asar/product-plugins/mittr-server.mjs`, so `build-desktop --flavor dev` exits 1. Reword it (for example "…in the person's own engine config") or allowlist it with a reason.
2. **F2 — the first sign-in on a fresh install reads the catalog twice (P3-09).**
   - Seen in both fresh HOMEs: two `GET /desktop/catalog` 0.3 s apart (08:43:13.540Z and .837Z in scenario B).
   - The second follows "the engine has its Mittr key for this run".
   - A sign-in after signing out of every account on the same machine read it once, as did adding a second account.
   - Likely the startup sync that waited for a first engine ready with an account, plus the sign-in's own sync.
3. **F3 — the desktop app reaches third parties without any Mittr feature asking (F37).** From the app's main process (the in-process server):
   - `api.github.com` at every start. This is upstream's Skills Catalog fetching repository metadata for its built-in sources (`skills-github-meta.json` is written at start; on hosted the same route asks `api.github.com`).
   - `registry.npmjs.org` each time Settings opens. The route was not attributed: on hosted none of the plugin-registry, skills, MCP, settings or guests routes asked npm.
   - One Cloudflare IPv6 address (`2606:4700:90:0:f22e:fbec:5bed:a9b9`) at every start. The host was not attributed: it does not match npm, `models.dev`, `opencode.ai`, `api.github.com`, `api-dev.mittr.asia` or `*.openchamber.dev`.
   - Opening Settings → Skills Catalog clones the curated repositories from `github.com` (about 20 git processes).

   Settings → General also offers "Send anonymous usage reports", and its default and egress were not measured. Owner call: disable or gate these upstream fetches in the Mittr product.
4. **F4 — someone else pressed Sign in in the test window (isolation).**
   - Scenario A's window started a sign-in 4 s after it appeared. The controller sent no input then.
   - The system browser fetched the stub's `authorizeUrl` (loopback only), and the `mittrcraft-dev://` callback came back to the test app, which then signed in as SA.
   - Not repeated in scenario B. The same as phase 2's F3.
   - Risk: the test app shares its bundle id and URL scheme with the installed Dev 1.x. If the test app had not been running, LaunchServices would have started the installed Dev 1.x.
5. **F5 — a withdrawn skill stays in a session that already used it (engine note).**
   - After the withdrawal and sync, new sessions (also in the same project) no longer list it, and loading it fails.
   - The session that had loaded it kept listing it in `<available_skills>` for at least 30 s.
6. **F6 — two connector processes for one location.** The app's home location got two stub processes, started at the same instant. They are probably the same folder under two spellings (`/var/folders/…` and `/private/var/folders/…`). Each project folder had one. On a HOME outside `/var` this may not occur.
7. **F7 — the packed server needs a sibling `mittr-opencode`.**
   - The packed tarball with a sibling `web`, as phase 2 used it for `--help`, does not start a server: "Cannot find module '…/mittr-opencode/src/identity-plugin.js' imported from …/mittr-server/src/mittr/identity.js".
   - It also needs its dependencies installed (`ldapjs`), as any npm package does.
   - The hosted install instructions should name the sibling, or the pack should carry it.
8. **F8 — an open My work list does not reload in place on a switch.** The SA list stayed on screen, unchanged, for 3.7 s after the switch call returned, until the window reloaded and the dialog closed. Reopening showed SB's row. No render showed SA's rows as SB's work.
9. **F9 — background recap calls use the Mittr model.** After turns, the app sent extra completions asking for a JSON "recap"/"suggestion" (four around the Go work session). They go through the shim and count against the person's Mittr quota. Owner note.
